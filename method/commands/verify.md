# Verify

`mde verify [scope]` (said to the agent: it runs the `mde verify` tool, then hands the audit to a second agent)

**In the loop.** While producing output, the agent verifies the Targets it is working on, as often as it needs, running the tool itself (never asking the user to): `mde verify --current` verifies every Target in progress, as [`work/targets.json`](../metamodel/work/targets.md) says (a record started, not yet completed), so the agent never has to name them; `mde verify --target <id>` verifies one, completed or not. Either prints each Target's rows and Checks, passed or not, and leaves the Evidence Package as it was; when every Target checked has Specs as its output, the build and the tests are skipped. In the loop the build is skipped when the sources are unchanged since the last passing build, only the Targets' own suites run when the application declares them (`mde:test:api`, `mde:test:ui`, `mde:test:unit`: [runtime scripts](../features/server/app-runtime-scripts.md)), and a failure the last run also had is marked *same as the last run*: each failure gets one fix, so it is a Finding, not another round. Fix everything a run reports before running it again. Generate, verify, fix, until it passes; then the Target may be marked completed ([How a stage runs](../strategy/guided.md#how-a-stage-runs)). A full `mde verify`, below, is what the user asks for and what writes the Evidence. Record what the loop found in Status, never as Evidence: only `mde verify` writes the Evidence Package, fingerprinted; one written or edited by anything else is refused (the Workbench shows none of its results).

Checks the output in scope (the slice the work's records name, without a scope) against its Targets, and keeps the result as Evidence. Only the completed Targets are graded; those in progress are measured and shown, never counted ([What the records decide](../metamodel/work/targets.md#what-the-records-decide)). It does two things, and keeps them apart:

1. **Verify.** Run `mde verify`. It proves by script and test run the Checks in each Feature's *Verify* (compiled into `targets/verification/<target>.md`): build, tests, coverage, diagrams, schema, Features, use cases, UI. It writes the [Evidence Package](../metamodel/evidence/evidence-package.md) (`evidence/README.md`), reporting each Check of each Target kept on its own: passed, failed, not run, not applicable, or waived. A Check no `mde verify` row measures is proven by scenarios tagged `@feature:<feature>/<promise>` (its id); so is each promise of each optional Feature the application applies, on each object that applies it. Write them when the Target or the Feature applies, rather than leaving a Check not run. For each completed Target whose evidence all passes (its audit aside), the tool writes `verified` on its completed records in `work/targets.json`; nothing else writes it.
2. **Audit.** What no script can judge is the second agent's, through [`mde audit`](audit.md): start it as a sub-agent when your tool can start one; otherwise tell the user, in the report, to open a new session and say `mde audit` there. The agent doing the work never audits its own output. Until the audit has run, the Evidence Package shows it not done, never passed.
3. On a failure, fix it once and verify again. If it still fails, stop: record it as a [Finding](../metamodel/work/finding.md) and leave the decision to the user. Never weaken a Check, a test, or a Target to get a pass, and never satisfy one with its shape alone (a placeholder file, a stub, an empty handler, a diagram of what does not exist): the audit reports it as fake, and it is a Finding against the work.
4. Report in Status: passed, failed, or blocked, for the verification and the audit separately, with what was checked, what was not, and the recommended next step. Never present an unrun check or an unaudited concern as passed, an inapplicable one as passed, or a waiver as anything but the user's.

When verification runs on its own (after every stage, or only when asked), and whether it includes the audit, is the Strategy's: see [Controlled](../strategy/controlled.md) and [Guided](../strategy/guided.md).

Review is the user's: their decisions on the output, through [`mde review`](review.md). Verify and audit inform it; they never replace it.
