# Update

`mde update` (said to the agent: it runs the `mde update-app` tool, then brings the application in line with what changed)

Brings the application's copy of the Method up to the installed MDE, and the application with it. The tool updates the Method's files; the agent does the rest. The user does not copy prompts or run anything.

1. **Update the Method.** Run `mde update-app` from the project root. It prints the versions (from → to), the Method files it updated, added, moved, or removed, the layout it migrated, and what needs attention; it writes a report under `work/current/method-update/` when files need merging, and commits only what it touched. If it says *Already up to date*, the Method's files are current: go on to step 3 with `mde changes`, in case an earlier update was never carried through.
2. **Merge what the application changed.** For each file the report lists as changed both here and upstream, or of unknown origin, MDE's version is saved beside the report. Merge it into the application's file: take MDE's change, keep the application's deliberate edits, and say which you kept. A file moved upstream but changed here: merge it into the new path, then delete the old one. Delete each saved copy once merged, and the report when none is left.
3. **Read what changed.** `mde update-app` prints the CHANGELOG entries between the two versions; when it says *Already up to date*, `mde changes` prints those after the version Status records as reconciled (`mde changes --since <version>` for another). Read those entries only, never the whole `method/CHANGELOG.md`. Each entry says what changed in the Method and, often, what an application must do.
4. **Bring the application in line.** For each entry, check the application against it: its Specs (a renamed section, a retired concept, a new required field), its App (a rule the code must now follow, a file the layout now expects), and its Work (`work/targets.json`, Status). Make the changes the Method now requires, as you would any work: in the owning Specs and App, traceable, and verified in the loop (`mde verify --target <id>` for each Target affected, completed or not, run yourself, fixed until it passes). A change that needs the user (a choice, a business decision) is a [Question](../metamodel/work/questions.md); one that cannot be made now is a [Finding](../metamodel/work/finding.md).
5. **Report.** In Status: the Method version from → to, the files merged, what the application changed to conform, what is left (with its Question or Finding), and the version now reconciled (`Method reconciled to <version>`), so the next update knows where to start. Commit coherent work as usual.

The update never changes the application's Goal, Strategy, or approved stages on its own. When a Method change bears on them (a Target added to the architecture's stack, a Strategy's rule changed), say so and let the user decide.
