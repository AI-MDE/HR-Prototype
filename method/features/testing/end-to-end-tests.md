# End-to-end tests with screenshots

## Purpose

Prove that people can do their work through the application itself, in a browser, against its real backend and database, and show it: every end-to-end scenario leaves screenshots of what the user saw, so a reviewer can read the run as a sequence of screens, not only as a pass count.

## Applicability

Applies, in every Strategy, once the application has a user interface that performs operations. It is not chosen by risk, and a manual check or a smoke test does not stand in for it. It complements the API scenarios ([readable test data](readable-test-data.md)): those prove the rules and terms, these prove the screens do the work.

## Impact on testing

- **Every page operation must be tested in the browser, with screenshots.** Every operation a page offers (create, edit, delete, each lifecycle operation, each use-case action) is performed by a passing end-to-end scenario in a real browser, against the real backend and database, and its outcome asserted on the screen and after a reload. Every use case with a screen is walked through its main flow. Every step leaves a screenshot. A page, or a page operation, that no passing browser scenario performed is untested, whatever API scenario proves the same operation; `mde verify` fails Pages tested and Operations tested through pages when none is, and keeps them partial until all are.
- **The real application, end to end.** Run against the application started the way `mde:start` starts it: its frontend, its backend, and its own end-to-end database, migrated and emptied before each scenario. Every page calls the application's API for every entity it shows or changes. A page that still reads from a prototype runtime or a substitute data source fails its scenario; it is a gap to report, never a reason to point the test at the substitute.
- **The same language.** End-to-end scenarios are Gherkin in the same common phrases as the API scenarios ([readable test data](readable-test-data.md)), tagged `@e2e`, with the use case they walk through, each page they use (`@page:<page>`), and each operation they perform through it (`@<entity>.<operation>`), so [Coverage](../../metamodel/evidence/coverage.md) counts the pages used and the page operations performed. Records are created from tables and named by label. UI phrases (signed in, opens a page, fills in, presses, performs an operation, the page shows, a section or a row found by its accessible name or its data, never its position) are generic and implemented once with the browser tool for every page, never per page.
- **A use case is walked, not clicked at.** Each use case with a screen has at least one scenario that performs its main flow as its actor, through the controls a person uses (stable selectors from accessible names), and asserts the outcome the user sees and that persists: after a reload, or in another list. Each [required operation a page renders](required-operation-ui-coverage.md) is performed by some scenario.
- **Signed in as the actor.** The scenario signs in, or selects the role through the development login, as the use case's actor; a refused operation is shown refused to a role that may not do it.
- **Screenshots of every step that changes the screen.** After each When step, and at the end of the scenario, pass or fail, and at the point of failure, capture the full page under `evidence/tests/screenshots/e2e/<feature>/<scenario>/NN-<step>.png`, numbered in order. A missing capture is reported. Never substitute a stale or generated image. Data is fictional.
- **Instrumented.** Run the frontend instrumented, and the backend too where it runs under the test's control, leaving the coverage summary in `evidence/coverage/raw/frontend/` with its `run.json`, so the pages' code exercised is measured by what these scenarios executed ([coverage-threshold](coverage-threshold.md)).
- **One command.** Declare `mde:e2e` (and run it from `mde:test`) so `mde verify` runs it. It starts and stops what it needs, and never stops a process it did not start.

## Impact on evidence

- The suite's [Test Report](../../metamodel/evidence/test-report.md), `evidence/tests/e2e.md`, is generated by the run:
  - one section per scenario, with its use case, its result, and its steps in order;
  - each step shows the screenshot taken after it;
  - a failed step shows its error beside the screenshot of the failure.

  A reviewer reads it as a storyboard of the use case.
- The Evidence Package's Tests row counts the end-to-end suite separately from the API scenarios, with a link to its report.

## Impact on web-ui

- Controls have accessible names (label, `aria-label`) that scenarios select by; a control a scenario cannot name is an accessibility gap, fixed in the page, not worked around with a CSS path.

## Verify

- `page-operations-tested` Is every page operation performed by a passing browser scenario (`mde verify`, Operations tested through pages: every operation, not some), and every page of the inventory used by one (Pages tested)?
- `screenshots-left` Did every browser scenario leave its screenshots (`mde verify`, Screenshots: one set per scenario)?
- `use-cases-walked` Does every use case with a screen have a scenario walking its main flow in a browser, with screenshots after each step and at failure?
- `e2e-report-generated` Is `evidence/tests/e2e.md` generated by the run, each step with its screenshot, and is the run instrumented for coverage?

## Audit

- Does every end-to-end scenario run against the real application, with no page served by a prototype runtime or substitute?
