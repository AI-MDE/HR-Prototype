## Purpose

What good evidence looks like, and how to check it: proof of what the application is, which a reviewer reads instead of the code. Its shape is defined by the [Evidence](../../metamodel/evidence/README.md) concepts.

It governs: [Evidence Package](../../metamodel/evidence/evidence-package.md), [Test Report](../../metamodel/evidence/test-report.md), [Coverage](../../metamodel/evidence/coverage.md), [Audit Report](../../metamodel/evidence/audit-report.md), and [Architecture Audit](../../metamodel/evidence/architecture-audit.md).

## Composed behavior

### Implementation coverage matrix  `[feature: code-coverage-matrix]`

- The application writes its implementation map, the inventory of what is built, `evidence/built/inventory.json`, from its own code on every build or test run: for each requirement (`use-case:<name>`, `rule:<slug>`, `operation:<Entity>.<operation>`, `term:<id>`) and each layer of its Architecture, the files that build it; and its **page inventory** (`pages`): every page it generated, each with its name, its `kind` (`list`, `detail`, `wizard`, or another), its `abe` or `useCase`, its file, its data source (`api`, or `runtime` when it still reads the MDE runtime), found from what its code actually calls, never written as a constant, the entities it shows, and the operations its controls perform. Since pages are not designed one by one, the inventory is how the evidence knows what was generated, against what the UI conventions want. Derive it from what the code declares (the model, the routes, the rule registry, the router and pages), never write it by hand; `mde verify` renders it in [Coverage](../../metamodel/evidence/coverage.md), for the API and for the pages.
- Rows come from the Specs, columns from the Architecture, never only from the code that happens to exist. A requirement the map does not place is not built, as far as the evidence shows.
- A not-built requirement is a [Finding](../../metamodel/work/finding.md) against the application; a built but untested one ([Coverage](../../metamodel/evidence/coverage.md)) is a Finding against the tests.
- Percentages of code run come from real instrumentation, never estimates, and belong to Test Coverage: say which runs were instrumented, and list excluded and unmeasured files, so a high number cannot hide unmeasured areas.
- Code coverage measures what was built and executed, not whether it is correct; test coverage answers whether the requirements are proven.

### End-to-end tests with screenshots  `[feature: end-to-end-tests]`

- The suite's [Test Report](../../metamodel/evidence/test-report.md), `evidence/tests/e2e.md`, is generated by the run:
  - one section per scenario, with its use case, its result, and its steps in order;
  - each step shows the screenshot taken after it;
  - a failed step shows its error beside the screenshot of the failure.

  A reviewer reads it as a storyboard of the use case.
- The Evidence Package's Tests row counts the end-to-end suite separately from the API scenarios, with a link to its report.

### Architecture audit  `[feature: evidence-architecture-audit]`

- The second agent writes each Audit Report to `evidence/audit/<target>.md`, and the Architecture Audit to `evidence/audit/architecture.md`, ending with the summary line *N genuine · M fake · K not-exercised*, which `mde verify` counts.
- The Architecture Audit judges each decision as written (resolved, traceable, consistent); the code's conformance to them is in the *Conformance* section of the server's and the web UI's Audit Reports, where a decision marked "not checked" is shown as such, never as conforming.
- Each violation, and each fake on an in-scope concern, is also recorded as a Finding.

### Evidence attachment  `[feature: evidence-attachment]`

- When invoked, `mde verify` writes the executable checks and details it supports. The Strategy determines whether an Evidence Package is required; do not claim it proves Target Checks the tool did not assess.
- A check that did not run is missing, not passed; a failed or missing check is never presented as passed. Leave out a row that does not apply (no UI, no deployment) rather than showing it as missing.
- Details are tool output (test runner reports, logs, screenshots, coverage reports) or tables derived from it. Do not add files the page does not link to.
- When the verified scope changes, an existing verdict no longer covers it. The page identifies the Goal and revision or working-tree state it assessed; only this page carries provenance.
- A release under the Controlled Strategy needs a current page showing every applicable check passed or waived, with blocking findings fixed or explicitly accepted by the user.

### Test coverage  `[feature: evidence-test-coverage]`

- Rows come from the Specs, not from the tests that happen to exist: each use case and its significant alternate paths, each business rule with its violating and boundary cases, each entity operation including prohibited ones, each page's required operations.
- A requirement with no scenario is a visible gap, not an omission. A row counts as covered only when a scenario naming it passed in the current report.
- Totals state covered, failing, and uncovered requirements separately.

### Use-case execution evidence and report  `[feature: use-case-execution-report]`

- A scenario that did not run is shown as not run, never as passed; a skipped scenario says why.
- Every scenario names the spec ids it proves (use case, business rule, operation, page), so test coverage can be derived from the reports.
- A suite that drives the running application keeps the application's own log for the run, so the report shows the server-side path executed, not only the test runner's view.
