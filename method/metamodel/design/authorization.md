# Authorization

Authorization says which [Roles](../requirements/role.md) may run each [Entity](../requirements/entity.md) operation. It is not written by hand: the [Use Cases](../requirements/use-case.md) already say it, since each names its actors and the operations it invokes. Its rules and checks are in the [application-design](../../targets/design/application-design.md) Target.

## Location

One file, `specs/design/authorization.json`, written by `mde authorization` and checked by `mde verify`. It is generated; change the use cases, not the file.

## Rule

- A role may run an operation when it is an actor of a use case that invokes that operation.
- A role may read an entity when it is an actor of a use case that invokes any of the entity's operations.
- A role whose spec declares `reads: all` in its frontmatter reads every entity: oversight, such as a system administrator's, which no use case describes.
- Nothing else is granted. An operation no use case invokes is run by no role (the Workbench's bypass, for development, still can).

## Structure

Each entity, then each operation, then the role ids (the `id` of each role's spec) that may run it:

```json
{
  "$comment": "Generated by `mde authorization` from the use cases. Do not edit; change the use cases.",
  "ServiceRequest": {
    "accept": ["dispatcher", "manager"],
    "read": ["dispatcher", "manager", "technician"]
  }
}
```

The runtime enforces it for the role a request names: an entity the file lists gets exactly these grants. An entity it does not list keeps the `## Authorization` table of its own spec, in applications from before this file.

## Relationships

- It is derived from the [Use Cases](../requirements/use-case.md): their Actors and Invoked Entity Operations.
- Its roles are [Roles](../requirements/role.md); its operations are those the [Entities](../requirements/entity.md) declare.
